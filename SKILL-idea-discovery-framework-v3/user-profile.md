# User profile: AI-native Product Manager

## Build-speed baseline

- **Assumed time commitment: ~20 hours/week.** The working assumption used to ground section 06's time-to-MVP estimates.
- **Baseline build window: ~4–8 weeks.** At ~20 hours/week, a *standard in-profile MVP* — one built from skills the user already has (see Product and Technical capabilities below) — ships in roughly 4–8 weeks.
- **How the window scales:**
  - *New-but-accessible learning* (a frontend framework not yet used, basic backend, public-API integration): roughly **2–3× the baseline window**.
  - *Significant new learning or specialized components*: **several times the baseline window** — or the baseline window itself if one specific collaborator takes a defined component.
  - *A critical component beyond solo reach* (specialized backend, licensed capability, deep domain): **partnership territory** — no realistic solo path within a sensible window.
- **Financial runway is not specified here** — capital is assessed per-idea in sections 06/07/08.

## Product capabilities

**Highly comfortable, demonstrated through direct work experience:**

- **Product strategy and discovery.** Identifying real painpoints, defining target users with precision, distinguishing strong from weak product hypotheses. Comfortable running structured discovery processes (this framework is itself a product of this comfort).
- **Product design and UX research.** Background-level expertise. Can design user experiences, run research, synthesize findings into product decisions.
- **Design execution.** Can produce design work — wireframes, prototypes, visual design — to a credible standard, with AI-assisted design tooling. **Design/UX is never a solo-buildability constraint** — including for design-led products where design is the commercial differentiator. (That a product *wins on design* is a section-03 defensibility question; it is not a section-06 build bottleneck for this user.)

**Working pattern:** the user thinks in systems and surfaces structural inconsistencies. Strong at framework design, clear communication, and iteration on complex problems. Default mode is to design carefully before executing, with willingness to revisit decisions when new information surfaces.

## Technical capabilities

**The user is not yet a developer in the traditional sense, but operates as an AI-native builder.** The relevant question for technical capability is not "can the user write this from scratch" but "can the user ship this with AI-assisted coding, using documentation-heavy workflows and review when needed."

**Current technical capability picture:**

- **Frontend frameworks:** comfortable. Can work with frontend frameworks for the kinds of UI typical of MVPs.
- **Backend:** no direct experience. Backend work would be done with AI-assisted coding and likely requires either careful scaffolding (working through documented patterns with Claude) or dev review for anything beyond simple API endpoints and standard patterns.
- **Databases:** somewhat comfortable with simpler options — Supabase, MotherDuck, Airtable. Can use these as the data layer for most non-enterprise MVPs. Complex database design (schema migrations at scale, query optimization, distributed databases) sits outside current capability.
- **Deployment:** an emerging capability, handled with AI-assisted tooling. Not yet a settled comfort area for complex or non-standard setups.
- **AI/LLM integration:** central capability area. Comfortable working with LLMs as both a coding partner and as product components.

**Working pattern for technical builds:**

The user works through a documented AI-assisted development workflow that gives a non-coder PM the structure to do real engineering work. Key features of the workflow:

- **Documentation-heavy.** The workflow leans on written specifications, structured prompts, and clear context-passing to AI assistants. Code that's well-specified upfront produces better results.
- **Git activities process.** Standard version control practices, with structured commits and branch management.
- **Dev reviews where needed.** For non-trivial work, the user incorporates developer review at appropriate checkpoints. This is not full pair programming with a developer — it's structured review of AI-assisted output for correctness, security, and reasonable architectural choices.

The workflow is reliable for standard product work; its limits at high architectural complexity are not yet established. Solo-buildability assessments should treat it as a real capability for standard builds, while treating highly novel or architecturally complex builds with caution.

## Operational capabilities

**Highly comfortable, demonstrated through direct work experience:**

- **Operational setup and process design.** Can set up business operations, design processes, write SOPs, and build operational structures from scratch.
- **GTM strategy.** Strong at strategic GTM planning — positioning, channel selection, message development, segment prioritization.
- **Finance and business operations.** Comfortable with business finance, basic accounting workflows, entity-level operational decisions.

**Somewhat comfortable, requires more effort:**

- **GTM execution.** The execution side of GTM (running campaigns, managing acquisition funnels, optimizing performance marketing) is less practiced than the strategic side. Strategy can be developed independently; execution may benefit from collaboration or contracted help.
- **Marketing execution.** Similar to GTM execution — strategic marketing is comfortable; tactical execution (running ads, writing high-volume copy, optimizing conversion funnels) is in the "can do but slower, may benefit from help" range.

## Sales and partnership capabilities

**Inferred (mark as M conviction in section 06 mappings until validated):**

- **B2B sales motion:** the user has product and operational experience that translates well to consultative B2B sales (problem identification, solution framing, stakeholder navigation). Direct experience with closing deals or running pipeline is not established in the profile and would benefit from explicit confirmation per idea.
- **Partnership development:** comfortable with the strategic side (identifying partnership opportunities, structuring deals). Execution depends on the specific kind of partnership — technical/data partnerships are different from distribution partnerships, which are different from capital partnerships.
- **Investor conversations:** if external capital becomes relevant for a specific idea, the profile does not assume practiced investor pitching. This may be a gap to address per-idea.

The "sales and partnership" section is the area of the profile with the most inference and the least direct evidence. Section 06 assessments touching this area should default to M or L conviction unless the user notes specific experience.

## Domain expertise

**Inferred — the user's domain expertise is broad-product, not deeply specialized in any single vertical.** This affects ideas in regulated or highly technical verticals:

- **Generalist product expertise:** broad understanding of how products work across categories, but not deep specialist knowledge in fintech, healthcare, legal tech, hardware, climate, or other specialized verticals.
- **For specialized vertical ideas:** the profile likely requires domain expertise input — either from a partner, an advisor, or significant ramp-up time before the build is credible. This is a real constraint and should be flagged in section 06 when the idea is in a specialized vertical.

## Learning trajectory

**The user is in a phase of active capability growth.** This matters for solo-buildability assessments — what's outside the profile today may be inside the profile in three months.

**Active learning areas:**
- AI-assisted coding (the development workflow is itself being refined).
- Deployment and infrastructure.
- The "operating as a builder" mindset more generally — moving from "PM who specs work for engineers" to "PM who builds work with AI assistance."

**Implications for solo-buildability:**
- The profile's capability range is expanding, but assessments should not assume the user will have learned a specific skill by the time an MVP is needed. Concrete capability today is what counts; future capability is uncertain.
- For ideas where the build window is long enough (6–12 months), the profile's growth trajectory means new capabilities can plausibly come online during the build. For shorter windows (around the baseline build window), the profile should be assessed as it stands today.

## Typical gaps requiring partnership or contracted help

Based on the capability picture above, the following are the most likely partnership or contracted-help gaps for ideas evaluated against this profile:

- **Complex backend architecture:** anything beyond standard API patterns and simple databases. Includes high-scale infrastructure, distributed systems, real-time data processing, complex security implementations.
- **Specialized domain expertise:** fintech compliance and licensing, healthcare regulatory frameworks, legal tech, regulated marketplaces, hardware/embedded systems, specialized scientific or technical fields.
- **High-volume execution marketing:** performance marketing at scale, paid acquisition optimization, content marketing at high cadence. Strategy is in-profile; execution at volume often warrants contracted help.
- **Investor pitching and fundraising:** if external capital is needed for an idea, the profile does not currently include practiced fundraising. Coachable, but not a default capability.
- **Specialized legal work:** general business legal navigation is manageable; specialized legal work (regulatory licensing, IP litigation, complex contracts) requires professional help.

These gaps are starting prompts, not absolute. Specific ideas may surface gaps not on this list, and specific ideas may turn out not to require something on this list. Section 06's Task 3 evaluates per idea, against this profile.
